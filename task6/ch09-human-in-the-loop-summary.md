# 第九章学习总结：Human-in-the-Loop

这一章让我理解了 Human-in-the-Loop 的作用：当 Agent 准备执行需要人工确认的操作时，可以先暂停，把操作内容交给人审核，再根据决定继续。例如，Agent 准备删除文件时，用户可以先查看文件路径，再决定是否允许删除。

**首先，怎么给工具添加人工审核？**

创建 Deep Agent 时，可以通过 `interrupt_on` 指定需要审核的工具。模型提出工具调用后，框架会在工具实际执行前检查规则；如果需要审核，就暂停运行，把工具名称、参数和允许的决策返回给调用方。也可以用 `when` 根据参数决定是否审核，但判断条件由开发者设计，框架不会自动识别所有风险。

| 配置 | 含义 |
| --- | --- |
| `True` | 调用该工具时触发审核 |
| `False` | 不因这项配置触发审核 |
| `allowed_decisions` | 指定审核方可以使用的决策 |
| `when` | 条件为 `True` 时审核；为 `False` 时不因该条件中断 |

这些规则由开发者事先配置；具体选择批准或拒绝的是审核方。未列入 `interrupt_on` 的工具不会自动因为该配置而触发审核。

**接下来，人可以作出哪些决定？**

用户可以选择 `approve` 按原参数执行，也可以选择 `edit` 修改参数后执行；如果不允许执行，可以用 `reject` 跳过这次调用并说明原因；对于 `ask_user` 这类询问工具，可以用 `respond` 直接提供回答，作为工具结果交给 Agent。具体允许哪些决定，由工具的审核配置确定。

| 决策 | 是否执行工具 | 接下来发生什么 |
| --- | --- | --- |
| `approve` | 尝试执行 | 使用原参数，向 Agent 返回工具结果 |
| `edit` | 尝试执行 | 使用修改后的参数，向 Agent 返回工具结果 |
| `reject` | 不执行 | 向 Agent 反馈这次调用被拒绝及原因 |
| `respond` | 不执行 | 把人的回答作为成功的工具结果 |

`reject` 适合拒绝删除或发送等操作；`respond` 适合由人直接回答 `ask_user` 一类工具。批准只表示允许执行，工具仍可能失败。

**然后，暂停后怎样恢复？**

恢复依赖 Checkpointer 保存线程状态。调用方展示待审核操作并收到决定后，用 `Command(resume=...)` 提交结果，再用相同的 `thread_id` 继续运行。如果一次审核包含多个工具调用，决策需要和待审核操作的数量、顺序对应。`version="v2"` 只是选择返回格式，方便通过 `result.interrupts` 和 `result.value` 读取信息；使用默认格式也可以中断和恢复。

| 返回格式 | 读取中断 | 读取图输出 |
| --- | --- | --- |
| 默认 `version="v1"` | 返回字典的 `__interrupt__` | 例如 `result["messages"]` |
| `version="v2"` | `result.interrupts` | 例如 `result.value["messages"]` |

恢复时还要访问同一份 Checkpointer 数据；`InMemorySaver` 在进程退出后无法恢复。不同并行节点如果分别产生多个中断，可以按 `Interrupt.id` 将回答映射到对应中断，不要与一次审核中按顺序对应的 `action_requests` 和 `decisions` 混淆。

**文件权限和工具审核有什么不同？**

`interrupt_on` 主要按工具及其调用条件配置；文件系统权限可以按操作类型和路径配置。例如，修改 `/secrets/` 下的文件时要求审核。权限规则还可以直接允许或拒绝操作；中断后仍然使用 `Command(resume=...)` 提交审核决定。文件权限有适用范围，不能默认它会限制所有自定义工具或系统命令。

| 文件权限模式 | 命中规则后的处理 |
| --- | --- |
| `allow` | 该权限规则允许操作 |
| `deny` | 直接拒绝操作 |
| `interrupt` | 暂停并请求人工审核 |

声明式子 Agent 可以继承主 Agent 的审核配置，也可以配置自己的规则；覆盖后的规则并不保证一定更严格，因此需要检查子 Agent 的实际权限。已编译子 Agent 的配置则应在其自身图中确认。

**最后，底层的 `interrupt()` 是怎样工作的？**

`interrupt_on` 封装了常见的工具调用前审批；当需要在其他业务步骤暂停，例如审核模型生成的草稿或向用户收集信息时，可以在合适的节点或中间件中直接使用 `interrupt()`。恢复时，发生中断的节点会从开头重新执行，直到 `interrupt()` 取得提交的恢复值。因此，要注意中断前的外部操作可能重复执行，也不要用宽泛的异常捕获把中断信号吞掉。

直接使用 `interrupt()` 时，恢复值的结构由业务代码决定；内置工具审批使用的 `resume={"decisions": [...]}` 是该审批流程的约定。同一个节点有多个 `interrupt()` 时，也要保持恢复重跑时的调用顺序稳定，避免回答错配。

这样看下来，HITL 的关键不是单纯弹出一个确认框，而是让 Agent 在需要人的位置暂停，并在收到决定后恢复工作。选择审核什么、允许哪些决定、如何处理可能重复的操作，仍然需要开发者结合具体业务设计。
