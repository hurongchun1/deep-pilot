# 第八章学习总结：长期记忆

这一章让我理解了 Agent 的记忆为什么要区分短期和长期：当前对话的消息、工具结果和任务进度通常服务于同一个会话，而用户偏好和项目知识可能在不同会话中都需要使用。例如，用户可以在一次对话中说“代码注释用中文”，以后开启新对话时，Agent 仍然可以参考这个偏好。

**首先，短期记忆和长期记忆有什么区别？**

短期记忆通常指同一个 thread 内的状态。配置 Checkpointer 后，相同 `thread_id` 的多次调用可以保存和恢复对话状态。长期记忆则适合保存需要跨 thread 复用的信息，例如用户偏好、项目背景和研究成果。这里的短期和长期主要描述使用范围；数据能否在程序重启后保留，还取决于 Checkpointer 或 Store 的具体实现。

| 对比 | 短期记忆 | 长期记忆 |
| --- | --- | --- |
| 使用范围 | 通常限于同一个 thread，可包含多轮对话 | 可以供不同 thread 访问 |
| 常见机制 | state + Checkpointer | Store + namespace |
| 典型内容 | 消息历史、工具结果、任务进度 | 用户偏好、项目知识、研究成果 |
| 重启后是否保留 | 取决于 Checkpointer 的实现 | 取决于 Store 的实现 |

例如，`InMemorySaver` 和 `InMemoryStore` 都只保存在内存中，进程退出后丢失；持久化 Checkpointer 或 Store 则可以在正确配置下跨进程保留数据。

**接下来，记忆文件存在哪里？**

本章使用 Backend 提供文件读写能力。`StateBackend` 把文件放在 Agent state 中，适合当前 thread 使用；`StoreBackend` 从 Store 读写文件，适合不同 thread 共享。`CompositeBackend` 可以根据路径选择后端，例如把 `/memories/` 路由到 `StoreBackend`，其他文件交给 `StateBackend`。它按照配置的路径规则选择后端，不会自动判断内容属于短期还是长期记忆。

| 组件 | 负责什么 | 例子 |
| --- | --- | --- |
| `StateBackend` | 通过 Agent state 读写文件 | 当前会话的草稿 |
| `StoreBackend` | 通过 Store 读写文件 | 跨会话使用的偏好 |
| `CompositeBackend` | 根据路径选择 Backend | `/memories/` 走 Store，其他路径走 state |

Backend 提供文件访问方式；StateBackend 的 state 是否能跨调用恢复，由 Checkpointer 负责。StoreBackend 数据是否跨重启保留，则取决于配置的 Store。

**然后，怎么区分不同用户或组织的记忆？**

Store 使用 namespace 组织数据。应用可以根据运行时 `context` 中的用户 ID 或组织 ID 生成 namespace，让同一个用户的不同会话访问同一组偏好，也让不同用户使用不同的数据组。Agent 级和组织级记忆也是类似的设计：共享的是指定的记忆内容，并不是自动共享所有人的完整会话。namespace 负责组织数据，应用仍需要验证身份和访问权限。

| 作用域 | 谁可以复用记忆 | 例子 |
| --- | --- | --- |
| 用户级 | 同一用户的不同会话 | 用户的代码风格偏好 |
| Agent 级 | 配置为使用同一份 Agent 记忆的会话 | Agent 的共享工作经验 |
| 组织级 | 同一组织中被授权的用户或 Agent | 组织政策和工作规范 |

要访问同一条记录，需要访问同一份 Store 数据，并使用相同的完整 namespace 和 key。相同用户 ID 本身不代表内容已经写入，也不代表应用已完成授权。

**记忆是怎么加载和更新的？**

`memory=` 指定要加载的已有记忆文件；`skills=` 指定 Skill 目录，让 Agent 在需要时读取做事方法。仅配置 `memory=` 不会保证文件自动创建，也不代表用户提出偏好后就一定完成写入。应用需要准备存储和文件，约定何时更新、更新哪个路径，并检查工具结果或 Store 内容，再用新的 thread 验证是否能够读取。

| 配置 | 指定什么 | 主要作用 |
| --- | --- | --- |
| `memory=` | 记忆文件路径 | 加载已有的背景、偏好或指令 |
| `skills=` | Skill 父目录 | 发现 Skill，并在需要时读取正文 |

在本章对应的 Deep Agents v0.7 行为中，`write_file` 会整体替换已有文件；保留旧内容并局部更新时，可先读取文件，再用 `edit_file` 修改。提示词可以指导 Agent 这样做，但不能保证每次都执行正确，因此要检查实际写入结果。

本章列出的应用场景包括用户偏好、自我改进、知识库累积和持续研究。其中自我改进指更新外部记忆或指令以影响后续行为，并不意味着模型权重自动训练。

**最后，设计记忆系统时要考虑什么？**

可以从六个问题入手：记忆使用多长时间、保存什么信息、谁可以使用、什么时候更新、什么时候读取，以及谁可以修改。例如，用户偏好可以按用户分组并允许更新；组织规则可以供成员共享，但限制普通 Agent 修改。还要根据需求选择内存或持久化存储，并注意多个会话同时更新同一文件可能产生冲突。

| 维度 | 需要回答的问题 | 示例 |
| --- | --- | --- |
| 持续时间 | 在哪些会话中使用，实际保留多久？ | 当前会话，或跨会话并在重启后保留 |
| 信息类型 | 记什么？ | 过去经历、事实偏好、做事方法 |
| 作用域 | 谁可以使用？ | 用户、Agent 或组织 |
| 更新策略 | 什么时候写入或整理？ | 对话中更新，或后台整合 |
| 检索方式 | 什么时候读取？ | 加载记忆文件，或按需读取 |
| 权限控制 | 谁能修改？ | 用户偏好可更新，组织规则只读 |

这样看下来，短期状态帮助 Agent 跟进当前会话，长期记忆让不同会话复用有价值的信息；Backend 负责文件如何访问，namespace 帮助组织共享范围。它们需要配合实际的读写逻辑和权限设计，才能形成可靠的记忆流程。
