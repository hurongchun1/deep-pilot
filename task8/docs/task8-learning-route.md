# Task8 学习路线：标注、代码实验与复盘

## 任务目标

学完后，能独立解释一次离线运行中的工具调用、工具结果、todos、Skill 和偏好记忆；能修改一条规则，并用实际运行结果说明影响范围。

学习采用两轮：先走标注路线建立全局地图，再做代码实验验证理解。每次实验按“预测 → 修改 → 运行 → 对照 → 总结”完成。本文提供练习要求，代码和复盘结论由学习者补充。

## 已知条件

- 当前有离线预设模型、三个场景、集成测试和运行证据，无需先接真实模型。
- 已有证据在 `evidence/offline-learning.json`，对应的是 learning 场景规划过程的七次调用，不包含此前保存偏好的调用，也不包含复制文件后的再次检查。
- `ScriptedModel` 按顺序返回预设回复；图、中间件、工具和文件读写仍实际运行。它会记录收到的消息，但不会根据工具结果选择下一条回复。
- 当前结构检查要求七个必要章节且正文非空，允许额外章节。结构通过不代表内容正确、计划可执行或任务已完成。
- 学习时长和开始日期尚未约定。以下以学习单元组织，按停止条件推进。

## 行动步骤

### 第一轮：沿用标注路线

只标三类内容：职责与边界、数据从哪来到哪去、暂未解决的问题。使用 `# ?框架` 挂起疑问；后续找到证据时，再补文件名和函数名。

| 站 | 阅读位置（相对 task8） | 自己动手留下什么 | 停止条件 |
| --- | --- | --- | --- |
| 0 | `evidence/offline-learning.json` | 抄七次工具调用；在 `tools.py` 查找，圈出未找到的两个名字；记录两个检查路径 | 能解释证据覆盖哪段运行，以及 `meaning` 排除了什么结论 |
| 1 | `scripted_model.py` 的 `planning_model`、`call`、`_generate` | 文件头职责/边界/依赖说明；虚拟路径流向；两条框架疑问 | 能说明调用顺序由谁决定、最后为什么停止 |

支线随后按需看：`sample_plan.py` → `skills/task-planning/SKILL.md` 与参考提纲 → `AGENTS.md` → `experiments/offline_demo.py`。真实模型入口最后看。

文件头依赖说明要准确：`scripted_model.py` 直接使用 `langchain_core` 和 `pydantic`，`planning_model` 内还导入 `sample_plan`；它被离线入口和测试导入。不要把“只依赖 langchain_core”写进标注。

站 3 特别留意：框架文件工具通过 backend 解析虚拟路径；自定义工具通过 `tools.PROJECT_ROOT` 和 `_inside` 处理真实路径。测试和离线入口同时设置这两处工作目录。不要把自定义工具的路径保护全部归给 backend。

### 第二轮：用代码实验检验标注

每次只做一个实验，记录结果后再进入下一个。先跑通现有基线；首次建立环境才需要执行同步命令。

在 `task8` 目录执行：

```powershell
uv sync --frozen
uv run --frozen pytest tests -q
uv run --frozen python -X utf8 experiments/offline_demo.py --scenario learning
```

离线入口会重新生成对应的 artifacts 和 evidence 文件。实验中先检查差异，不要把旧 JSON 当成新代码的运行结果。以下命令是学习时的操作要求，不表示本文创建时已经执行。

#### 实验 A：追踪工具结果如何回到模型

- 入口：测试中的 `workspace`、`model.prompts`、最终 `messages` 和流式 `snapshots`。
- 编码任务：新增一个聚焦的离线测试或观察脚本，按调用 id 找到 `save_plan` 的工具结果，确认它进入下一次模型调用；记录模型回复、工具结果、todos 的先后变化。
- 先预测：调用参数、返回消息和状态字段是同一个东西吗？哪个字段能关联调用与结果？
- 验收：用 `tool_call_id` 关联一次调用与结果，并在后续 prompt 中找到该结果的内容；展示 todos 从进行中到完成的证据，不把相邻快照重复值误认为重复调用。
- 复盘问题：结果确实回到模型，为什么仍不能证明离线模型会理解结果并调整行动？

先用当前 `prompts` 字符串观察内容；若要进一步验证消息类型或调用 id，可增加结构化观察记录，避免仅凭字符串推断消息结构。

#### 实验 B：让结构检查失败一次

- 入口：独立构造 `ScriptedModel`，复用当前 `call`、图和临时工作区。
- 编码任务：保存缺失或空章节的计划，读回并调用检查；检查最后一条预设回复会说什么。
- 先预测：`check_plan` 的 `ok=false` 会自动让脚本改口、重试或中止吗？
- 验收：能看到 `missing` 或 `empty`；同时记录最终回复。若仍预设“结构检查通过”，明确指出它与工具结果矛盾。
- 复盘问题：prompt 中的要求、检查工具的返回值、程序强制阻断，分别能保证什么？若要求失败后必须停止，应在哪一层增加控制？

现有检查失败用例可作起点；本实验增加的是对失败结果与后续回复关系的观察。

#### 实验 C：从七个必要章节改为八个

- 新要求：所有计划必须包含有正文的“复盘记录”；未执行的计划应写明待执行后的复盘内容，不能编造完成结果。
- 先搜索：七个章节在哪些地方被定义、生成、教给模型、说明和验证？先列影响清单，不先猜“改几处”。
- 分两步：先只给计划追加第八章，观察当前检查器是否接受；再将它设为必要章节，让旧的七章计划检查失败。
- 编码任务：同步检查规则、样例生成和参考提纲；按实际搜索结果同步说明与测试，重新生成受影响的离线产物和证据。
- 验收：旧七章内容缺少“复盘记录”时失败；新增但空白时失败；有正文时通过；三个预设场景的集成测试和离线入口通过。
- 复盘问题：哪些地方决定程序行为，哪些只影响模型提示，哪些只是历史输出？为什么只改 Skill 不够？

历史产品示例和旧证据保留原有含义，不要把它们改造成新版运行证明。不要为了通过测试而简单删除失败断言。

#### 实验 D：分清偏好文件和会话状态

- 入口：`save_preference`、`MemoryMiddleware`、`InMemorySaver` 和跨会话测试。
- 编码任务：用临时目录分别比较“新图读取已保存偏好”和“使用同一 checkpointer 恢复同一 thread”；再比较同一 checkpointer 下的新 thread。
- 先预测：偏好文件、messages、todos 分别由谁保存和加载？新 thread 为什么能看到偏好，却不应被当作继承了上一 thread 的对话？
- 验收：分别用 prompt 内容和 checkpoint 状态验证，不只看最终自然语言回复；不改项目真实偏好文件。
- 复盘问题：删除 checkpointer 与删除偏好文件，对这两种记忆分别有什么影响？

### 每次实验后填写的复盘模板

将下面模板复制到本文末尾，或独立保存为 `docs/notes/<实验名>.md`。先写预测，再运行；代码不必大段复制，保留文件、函数、命令和关键证据即可。

```markdown
### 实验名与日期

- 要回答的问题：
- 运行前预测（含理由）：
- 修改位置与目的：
- 运行命令：
- 实际结果（关键输出/消息/状态/文件差异）：
- 与预测的差异及解释：
- 本次证据能证明什么，不能证明什么：
- 关联标注（文件与函数）：
- 尚未解决的问题：
- 下一步最小验证：
```

## 验收标准

- 标注完成：合上代码，能解释七次调用、两个框架工具的来源、文件路径和结构检查边界。
- 实验完成：每项有运行前预测、自己写的改动、实际证据和复盘；失败实验同样可以是成功的学习成果。
- 修改完成：涉及程序行为时运行相关测试；章节规则的联动改动还需检查三个离线场景及新生成的产物。
- 最终总结：能区分“预设回复驱动的流程通过”“真实模型自主选择工具”“工具结构检查通过”“任务实际完成”。

## 风险与调整

- 标注变成逐行翻译：只保留职责、边界、数据流和疑问；能直接读懂的语法不重复解释。
- 一次研究过多框架实现：先记录疑问，完成站 3 和实验 A；仍有具体缺口时再查对应实现。
- 只看成功路径：优先完成实验 B，观察错误结果是否真的影响后续行为。
- 修改过大无法解释结果：一次只改变一个变量；实验 C 刻意分成“允许额外章节”和“增加必要章节”两步。
- 文档写成源码抄本：只记录理解发生变化的地方，并关联具体运行证据。
