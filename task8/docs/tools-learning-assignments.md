## 主题一：给 Agent 提供一项工具能力

应用：把一个普通 Python 功能包装成可描述、可传参调用的工具。

- 阅读：tools.py 中的 @tool 函数；agent.py 中的 tools 注册列表。
- 演示：实验 1，函数 tool_definition。观察工具名称、描述、参数结构和 invoke 返回值。
- 自己改：为示例工具增加必填的 deadline 参数；比较原调用和补齐参数后的调用。记录真实异常，不提前假定异常类型。
- 草稿要回答：普通函数、工具对象、注册给 Agent 三者是什么关系？docstring 与类型注解提供什么信息？工具的 invoke 和图的 invoke 分别运行什么？
- 完成条件：能调用自己改过的工具，并解释为什么这个实验没有证明模型会主动选择它。

### 提升后的正文主线

1. **能力与输入契约**：普通函数如何变成工具对象；名称、description、输入 schema 分别提供什么信息。展示生成的 schema，不只解释装饰器语法。
2. **类型与业务校验**：对比普通 str、限定取值的 Literal 或枚举、结构化输入模型；哪些错误能在执行函数体前发现，哪些必须在函数内判断。类型注解不能代替所有业务约束。
3. **完整调用循环**：用户请求 → 模型发出 tool_calls → 框架找到工具并校验输入 → 执行 → ToolMessage 回到消息 → 模型继续。用调用 id 与 tool_call_id 关联请求和结果，而不是只看最终回答。
4. **失败如何反馈**：区分参数校验失败、Python 异常、返回“参数错误”字符串、正常返回但业务检查为 false。直接 invoke 与图内执行的错误传播可能不同，应核对实际工具节点和错误处理配置。
5. **结果与状态**：普通工具返回数据不等于任意图字段自动更新；以 write_todos 使用 Command 更新状态为对照。工具输出、图状态和磁盘副作用分别是什么。
6. **边界与设计取舍**：读取工具与写入工具的副作用不同；模型重复请求、框架重试、并发执行时是否安全。工具粒度过大或过小分别给模型和程序带来什么负担，用具体案例说明。

### 递进实验

- **核心**：保留原有必填参数实验，再增加限定取值的参数，对照“输入校验失败”与“函数返回业务错误”。打印实际异常/消息，不假定框架一定替你重试。
- **核心**：注册到真实模型，观察至少一次实际工具请求及返回，用 id 关联；若模型未调用，记录未调用，不把结果描述当执行证据。
- **进阶**：对一个临时文件写入工具重复调用相同参数，对照“追加”与“覆盖”；判断何时会重复产生副作用。仅设计幂等方案即可，不必立刻建设完整去重系统。

## 主题二：Backend 的存储、执行、组合与权限机制

应用：为 Agent 选择文件存放位置、持久化范围及命令执行能力；通过路径路由组合不同 backend，再配置内置文件工具的访问权限。

独立知识库笔记建议命名为《Deep Agents Backend：存储方式、执行能力与权限控制》。正文不依赖任务编号、仓库路径或课程进度。Path 拼接与 mkdir 只作为必要语法简述，不作为主体。

### 建议的正文顺序

1. **Backend 是什么**：先画出“模型提出工具调用 → 框架文件工具 → backend → 存储或执行环境”的关系。说明 backend 接口不意味着所有实现都支持 shell。
2. **五种 backend 对比**：按数据位置、会话范围、重启后行为、执行能力和适用场景比较，而不是只列类名。
3. **逐类解释关键参数与最小示例**：参数说明紧挨可观察的使用例子；不必罗列全部可选参数。
4. **StateBackend 与 checkpointer、StoreBackend 与 store 的关系**：分别解释职责、配置位置及生命周期，区分跨 thread 与跨进程。
5. **CompositeBackend 的路径路由**：解释 default、routes、最长前缀匹配，以及匹配后的路径怎样交给目标 backend。
6. **FilesystemPermission 的规则与边界**：解释路径匹配、读写操作、规则顺序、默认允许与中断审批，并用允许/拒绝例子验证。
7. **选型与组合实例**：会话草稿放 state、共享资料放 store、本地项目文件放 filesystem；明确 shell 的实际访问范围。

补充已整理内容：七项内置文件工具由 FilesystemMiddleware 提供并调用 Backend，不把 Backend 简单等同于某一种虚拟文件存储。正文需覆盖按行分页、媒体读取限制、ls 实际返回、glob/grep 区别、整体覆盖与精确替换、删除行为。当前安装实现的 write/write_file 支持创建或覆盖，不能沿用旧版拒绝覆盖的表述。

### 每类需要讲的重点

| 类型 | 重点机制与参数 | 示例要观察的现象 |
| --- | --- | --- |
| FilesystemBackend | 本地文件系统；root_dir、virtual_mode；可按需补充文件大小限制 | 虚拟 /notes.md 实际落在哪；virtual_mode=True/False 对绝对路径的处理有何不同 |
| LocalShellBackend | 在文件操作之外提供 execute；root_dir、timeout、max_output_bytes、env、inherit_env | 运行无副作用命令，观察工作目录、输出与退出结果；超时如何处理 |
| StateBackend | 文件存放在图 state 的 files；当前版本需要图执行上下文；与 checkpointer、thread_id 的联系 | 同 thread 后续调用能否读到；新 thread 是否隔离；无 checkpointer 与有 checkpointer 的差异 |
| StoreBackend | 文件存放在 LangGraph Store；当前安装版本的 namespace 工厂与可选显式 store | 不同 thread 使用相同 namespace 是否共享；切换 namespace 是否隔离；内存 store 与持久化 store 的区别 |
| CompositeBackend | default 与 routes；最长前缀匹配；路由前缀处理 | 不同路径落到哪个 backend；未匹配路径走哪里；路由不等于同步复制文件 |

### 必须准确解释的边界

- StateBackend 管理 state 内文件；checkpointer 负责状态快照与恢复。不能写成“StateBackend 是 checkpointer”，也不能说没有 checkpointer 就完全不能运行。
- StoreBackend 通过 store 读写，并用 namespace 控制作用范围。跨 thread 可共享不等于进程重启后必然保留；InMemoryStore 仍是内存实现。
- virtual_mode 规定文件操作的路径映射与检查，不是操作系统沙箱；不能据此推断 LocalShellBackend.execute 被限制在根目录内。
- FilesystemPermission 是传给 create_deep_agent 的 permissions 规则，在内置文件工具层执行，不是给每种 backend 自动附加的底层访问控制。
- 权限规则不自动覆盖自定义 save_plan/read_source 直接访问磁盘的代码，也不保护直接 backend 调用或任意 shell 命令。自定义工具仍要实现自己的限制。
- 当前权限规则按声明顺序取第一个匹配项；未匹配默认允许。写“只允许某目录”时需要验证兜底规则，不能只写一条 allow 就认为其他位置被禁止。

### 分阶段实验要求

1. 先完成 FilesystemBackend 最小示例，观察 virtual_mode 的路径映射；使用临时目录。
2. 在图内使用 StateBackend，比较同 thread 和新 thread；再使用 StoreBackend 对照相同/不同 namespace。此阶段先用内存 checkpointer 与 store，明确没有验证进程重启持久化。
3. 用 CompositeBackend 将临时草稿、共享数据、本地文件路由到不同实现，检查最终数据实际保存位置。
4. 通过 Agent 的内置文件工具测试权限：允许读取资料、拒绝写资料、允许写产物；再用自定义工具作对照，检查权限是否覆盖，避免误判。
5. 最后单独观察 LocalShellBackend 的执行能力，使用打印工作目录等无副作用命令，不用 shell 访问范围替代文件权限结论。

### 可选的进一步深化

- **生命周期选型**：同一个 thread_id 配合不同 checkpointer 实例、相同 namespace 配合不同 store 实例，分别会怎样？解释“身份标识”和“保存载体”不能互相替代。
- **路由别名**：两条虚拟路由指向相同底层 store/namespace 后，相同内部文件名是否共享？不要只看路径名字就推断数据隔离。

## 主题四：给 Agent 接入会话状态与长期记忆

应用：让 Agent 延续当前对话，同时按配置加载跨会话复用的信息。重点是组件如何接入及其作用范围，而不是单独研究文件写入算法。

### 建议的正文顺序

1. **三种职责先分开**：state 承载当前运行数据，checkpointer 保存与恢复 thread 状态，MemoryMiddleware 加载指定记忆文件并加入系统提示；Store 提供另一个可按 namespace 组织的存储接口。
2. **会话如何继续**：配置 checkpointer 与 thread_id，解释同 thread 的 messages/todos 怎样延续，新 thread 为什么不直接继承这些状态。
3. **记忆文件怎样加载**：backend、sources、system_prompt 的参数含义；追踪 before_agent 返回 memory_contents，再由模型调用包装逻辑注入提示的过程。
4. **新增偏好怎样保存**：用户明确要求记住 → 模型请求 save_preference → 工具写文件 → 后续加载。MemoryMiddleware 不等于自动保存全部对话。
5. **文件记忆与 StoreBackend 怎么选**：文件适合怎样的配置和资料，Store/namespace 怎样组织跨 thread 数据；两种方式不是必须同时配置的同一套存储。
6. **记忆范围与更新时机**：区分任务、会话、项目、用户范围；已存在 memory_contents 时跳过加载的行为怎样影响新鲜度。持久化介质不自动决定语义范围。
7. **最小组合实例**：同一工作空间中先明确保存偏好，再用新 thread 读取；同时用同 thread 的追问观察会话延续，区分两种现象。

### 阅读与核心实践

- 阅读 save_preference、MemoryMiddleware 配置和关键 hook、真实入口中的两个 thread，以及 checkpointer 的使用位置。
- 使用独立实验目录和真实模型：第一轮明确保存偏好，第二个 thread 提问；核对文件、memory_contents 与实际模型输入，不只看回答风格。
- 保持原 thread 继续追问，对照新 thread，说明“聊天历史延续”与“加载共同偏好”不是同一种机制。
- 文件更新后继续旧 thread，再建立新 thread，对照已有记忆副本是否刷新；以实际状态和消息为准。
- 将并发写入覆盖作为 save_preference 的一个注意事项，用简短时间线说明即可。锁、原子替换和数据库事务不作为本篇主线，也不要求全部实现。

完成条件：能为自己的 Agent 选择并接入合适的会话/记忆配置，解释谁保存、谁加载、谁决定作用范围；不将文件写入成功等同于模型已加载或已遵守。

### 增加的机制与设计取舍

| 深入方向 | 必须解释的内容 | 对照实验 |
| --- | --- | --- |
| 生命周期 | before_agent/after_agent 与 before_model/after_model、wrap_model_call/wrap_tool_call 分别包围什么范围 | 在真实多轮工具流程中记录调用序号、阶段与调用 id；不要预设固定模型调用次数 |

| 状态更新 | 返回的局部状态更新如何合并；字段 reducer、Command 与请求 override 作用不同 | 分别更新自定义 state 字段、追加消息和只修改模型请求，观察最终 state 与模型输入 |
| 失败与重复执行 | 工具异常、模型异常发生在哪一层；重试是否重复外部副作用 | 独立实验中注入一次可控异常，先观察不重试的传播，再决定哪层适合处理 |
| 同步与异步 | 当前入口使用 invoke/stream，异步入口需匹配对应 hook 实现；不是写了任意同步 hook 就假设所有异步路径一致 | 作为进阶对照，按当前安装版本补齐异步实现，再比较日志，不凭命名推断行为 |
| 职责选择 | 系统提示、普通工具、middleware、callback 分别适合承担什么 | 用“打印日志、注入偏好、更新待办、写文件”四个需求说明选择与理由 |

## 主题七：HITL——人工审批、中断与恢复

应用：让 Deep Agent 在指定操作执行前暂停，将拟执行的工具与参数交给人审阅，再按批准、修改或拒绝的决定继续运行。

独立知识库文档建议命名为《Deep Agents HITL：工具审批、中断与恢复》。本节目前是章节提纲，尚未生成完整文章或运行新增审批示例。

### 建议的正文顺序

1. **是什么，为什么需要**：模型选择工具与人工授权的分工；选取写文件这一明确动作作为例子，不以一句“是否继续”的自然语言回复替代执行层暂停。
2. **怎样接入 Deep Agent**：说明工具级 interrupt_on、相关人工介入中间件与文件权限 mode="interrupt" 的关系；按实际版本核对支持的配置，不将三种入口说成每次都必须重复注册。
3. **为什么需要 checkpointer 与 thread_id**：暂停时需要保存什么状态，恢复时为什么应回到原 thread；内存 checkpointer 与持久化实现对跨进程恢复有什么影响。
4. **中断时返回什么**：展示实际中断结果中的待审批操作、工具名、参数和审批选项；区分正常最终回答与尚未完成的暂停状态。
5. **人怎样提交决定**：分别说明批准、修改参数、拒绝后的预期路径；所允许的决定受中断配置限制，不假设所有操作都开放全部选项。
6. **恢复后怎样继续**：使用框架恢复机制继续原执行；区分恢复操作与重新提交用户任务。检查工具实际结果和副作用，不能只看模型说“已批准”。
7. **和其他组件怎样协作**：Backend 提供实际文件操作，工具提供执行入口，中间件拦截，checkpointer 保留状态，审批界面或调用端收集人的决定。
8. **失败与重复执行边界**：人拒绝不等于回滚已发生的全部操作；暂停也不代表进程一直阻塞等待。恢复与重放的细节按当前版本核对，不能承诺任意副作用天然只执行一次。

### 就地最小完整代码示例要求

- 第一段完整示例：真实模型 + 一个只写临时文件的工具 + 工具审批配置 + checkpointer，调用后打印中断详情，并检查审批前目标文件是否存在；此时不自动替用户批准。
- 第二段完整示例：同一个可运行程序中用终端输入收集批准、修改或拒绝，并按原 thread 恢复，打印恢复结果及文件状态。示例应包含必要文件与工具定义，不依赖第一段运行时留下的对象。
- 若另讲 FilesystemPermission 的 interrupt，给出本节自己的最小配置和执行代码。Backend 文章只保留简述，不要求读者先运行另一篇的代码。
- 不需要并发多操作审批、复杂前端或 Subagent 审批链才能理解基础流程；这些按需作为后续扩展。
- 模型未请求目标工具时，不算触发了审批机制；应保留实际中断及执行证据。完整知识库以文内代码示例呈现，不写配套脚本或作业任务。

### 容易混淆的地方

- **模型询问与框架中断**：文字上问“是否继续”不代表工具执行被阻止。
- **工具可用与操作获批**：注册能力不代表每次调用已经得到授权。
- **暂停与完成**：产生中断结果时，任务可能仍在等待人工处理。
- **保存状态与保存工作目录**：checkpointer 保存执行状态，不自动备份或回滚磁盘文件。
- **恢复与重跑**：恢复使用原有执行状态，不是另开 thread 再发一次任务。
- **拒绝与撤销**：拒绝待审批操作，不等于撤销此前已经发生的全部副作用。
- **权限拒绝与审批中断**：deny 直接拒绝；interrupt 等待人工决定，两者的后续处理不同。
- **示例决策与真实人工决策**：代码里硬编码批准只演示恢复接口，不应声称已完成真实人工审阅。

完成条件：能构建一次真实可观察的“触发中断 → 展示操作 → 人工决定 → 恢复执行”流程，说明每个组件职责，并验证审批前后实际发生的操作。此能力尚未在当前学习示例中运行验证。
