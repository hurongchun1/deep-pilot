# pandas CSV 清洗两周学习与交付计划

## 任务目标

在两周内（每天 1 小时，共约 14 小时）从"会 Python 基础"达到"能独立用 pandas 清洗一份 CSV"，最终交付两项产物：

1. 一个可运行的清洗脚本：读入原始 CSV，完成清洗后输出干净 CSV，脚本内区分读取、体检、清洗、校验、输出各环节。
2. 一份前后数据对照：展示清洗前后的行数/列数、缺失值、重复行、字段类型、关键字段分布等指标变化，以及每条清洗规则的作用说明。

## 已知条件

用户明确提供：

- 起点：具备 Python 基础（未说明具体掌握程度，判断标准列为待确认）。
- 技术方向：使用 pandas 清洗 CSV 数据。
- 时间预算：2 周，每天 1 小时。
- 预期交付：一个清洗脚本 + 前后数据对照。

以下为建议（非用户给定，可拒绝或调整）：

- 建议在第 1 天就固定一份练习用 CSV，而不是等到有真实业务数据才开始；练习数据里应包含缺失值、重复行、日期格式不统一、数字混入单位或空格等常见问题。
- 建议每天固定 60 分钟分配：5 分钟回顾昨天 + 40 分钟主任务 + 10 分钟记录与产物落盘 + 5 分钟缓冲。
- 建议把脚本拆成函数并保留一个 `main()` 入口，便于最后一天从零重跑验收。
- 建议每步清洗规则都在日志或对照表中留一行"问题 → 规则 → 影响行数"，这是"前后对照"最容易验收的形态。

## 行动步骤

依赖关系：第 1–6 天为单点能力学习，彼此可微调顺序；第 7 天首次串联；第 8–11 天在串联后的脚本上迭代；第 12–14 天收尾。第 7 天和第 14 天兼作缓冲，落后时优先用这两天补齐。时间均以"第 N 天（约 60 分钟）"相对表述，未指定开始日期。

### 第 1 周：理解与单点练习

- 第 1 天（约 60 分钟）：环境与数据准备。确认 Python 版本可用、能安装并导入 pandas；确定一份练习 CSV（真实数据或自造数据均可）；建立项目目录（如 `data/raw/`、`data/clean/`、`scripts/`、`reports/`）与一个工作日志文件。
  - 产物：可导入 pandas 的环境、一份原始 CSV、项目目录、工作日志初始记录。
  - 完成标准：`import pandas` 无报错并打印版本；原始 CSV 能被记事本/编辑器打开并看清表头。
- 第 2 天（约 60 分钟）：读取数据。练习 `read_csv` 常用参数（分隔符、编码、`dtype`、`na_values`、`usecols`）以及 `head`、`shape`、`columns`、`dtypes`、`info`。把首次读取结果记为"清洗前基线"。
  - 产物：读取代码片段 + 清洗前基线记录（行数、列数、字段类型、前几行样例）。
  - 完成标准：能无告警地读入数据，并在日志中写下清洗前的行数、列数与类型清单。
- 第 3 天（约 60 分钟）：数据体检。统计每列缺失率、唯一值数、重复行数、数值列的分位数与极值、疑似异常取值（如金额带单位、日期格式混杂、空格与大小写不一致）。
  - 产物：一份"问题清单"表，字段为：列名 / 问题 / 举例 / 计划处理方式 / 处理优先级。
  - 完成标准：问题清单覆盖缺失、重复、类型、格式四类，并给出至少 5 条具体条目；每条都有对应处理方式。
- 第 4 天（约 60 分钟）：选列、重命名与类型转换。练习列选择、`rename`、`astype`、`to_numeric(errors=...)`、`to_datetime(errors=...)`，处理数字列混入字符与日期多格式的情况。
  - 产物：类型转换代码 + 转换前后 `dtypes` 对照。
  - 完成标准：至少 1 个字符型数字列和 1 个日期列被正确转换，转换失败的值被显式识别而非静默丢弃。
- 第 5 天（约 60 分钟）：缺失值处理。练习缺失识别、按列删除、常量填充、均值/中位数填充、分组填充或前向填充，并讨论每种选择的适用条件。
  - 产物：缺失值处理代码 + 每列"清洗前缺失率 → 处理方式 → 清洗后缺失率"小表。
  - 完成标准：每列缺失都有明确处置决定和一句理由，不出现"随手填 0"却无说明的情况。
- 第 6 天（约 60 分钟）：去重与文本清洗。练习重复行识别与删除、`str.strip`/`str.lower`/`str.replace`/正则替换，处理多余空格、单位混入、大小写不一致。
  - 产物：去重与文本清洗代码 + 被修改行数统计。
  - 完成标准：重复行数量有前后对比数字；文本列取值集合在清洗后明显收敛（给出唯一值数变化）。

### 第 7 天：首次串联（兼缓冲）

- 第 7 天（约 60 分钟）：复盘与脚本 v0.1。把第 2–6 天片段按顺序写进一个脚本，跑通"读取 → 体检 → 清洗 → 输出"，并补写第一周小结（哪些步骤已稳定、哪些仍不稳定）。
  - 产物：可运行的 `clean_csv.py` v0.1、清洗后 CSV 文件、第一周小结。
  - 完成标准：脚本从原始 CSV 一次运行即可产出清洗后文件，无手工改中间结果；小结写出 2 条以上待改进点。

### 第 2 周：工程化、校验与交付

- 第 8 天（约 60 分钟）：异常值与取值范围。练习条件筛选、`clip`、`where`/`mask`、按分位数或业务区间识别越界值，并把处置方式写进问题清单。
  - 产物：异常值处理代码 + 越界规则表（字段 / 合理区间 / 越界处理 / 影响行数）。
  - 完成标准：至少 2 个字段有明确区间规则，且越界行数可复现统计。
- 第 9 天（约 60 分钟）：清洗合理性校验。用 `groupby`/`agg`/`pivot_table` 抽查清洗前后分组结果是否合理，做守恒性检查（如清洗前后总额差异应可被删除行解释）。
  - 产物：校验代码 + 校验结论记录。
  - 完成标准：给出至少 1 条守恒或对账结论，并能解释差异来源。
- 第 10 天（约 60 分钟）：脚本工程化。拆成 `load_data`、`audit_data`、`clean_data`、`validate_data`、`save_data` 等函数，加 `main()` 入口与参数（输入路径、输出路径），关键步骤打印日志（处理前后行数、改动行数）。
  - 产物：模块化脚本 v1.0。
  - 完成标准：改一个路径参数即可对新 CSV 运行；日志能看出每步影响了多少行。
- 第 11 天（约 60 分钟）：前后数据对照。写一个对照生成环节（函数或独立小脚本），输出对照表：行数、列数、缺失单元格总数与缺失率、重复行数、字段类型变化、关键字段唯一值数与分布对比，并按"问题 → 规则 → 影响行数"附规则清单。
  - 产物：`data/clean/` 下的清洗后 CSV + `reports/` 下的前后对照表（CSV 或 Markdown，按第 11 天实际选择的格式）。
  - 完成标准：对照表能仅凭数字回答"删了多少行、补了多少空、改了多少类型"，不需要看代码。
- 第 12 天（约 60 分钟）：测试与边界情况。用空文件、全缺失列、编码异常、日期格式混杂等小样本试跑，记录失败表现与处理策略（报错退出、跳过该列、还是显式告警）。
  - 产物：边界用例清单 + 脚本对每种情况的当前表现记录。
  - 完成标准：至少 3 个边界用例有明确预期行为，其中 1 个已在脚本中加断言或告警。
- 第 13 天（约 60 分钟）：整理交付物。写 README（用途、依赖与版本、目录结构、运行命令、每列清洗规则说明、已知限制），并在干净环境下按 README 从零跑一遍。
  - 产物：README + 脚本 + 清洗后数据 + 前后对照表，构成完整交付包。
  - 完成标准：只读 README 就能把脚本跑成功；清洗规则说明与实际代码一致（逐条核对，不凭记忆）。
- 第 14 天（约 60 分钟）：复盘与演示（兼缓冲）。照对照表讲 5 分钟"这份数据脏在哪、我怎么处理的、处理完是否可信"，记录遗留问题与下一阶段方向（如多表合并、时间序列、性能优化）。
  - 产物：5 分钟讲解要点稿 + 遗留问题清单 + 下一步学习方向。
  - 完成标准：能不看代码说出 3 条以上清洗规则及其影响行数；遗留问题至少 2 条并标注是否阻塞交付。

负责人：未指定。本计划默认由用户本人独立完成，若需他人提供真实数据或审核规则，在第 1 天确认。

## 验收标准

交付时逐项核对，均为"检查动作 + 通过条件"：

1. 脚本可运行：在只改输入/输出路径的情况下，一条命令从原始 CSV 生成清洗后 CSV，过程中不手工修改中间文件。
2. 清洗规则可解释：每条规则能对应问题清单中的一条问题，并给出受影响行数或单元格数。
3. 前后对照可核对：对照表含行数、列数、缺失率、重复行数、字段类型变化、关键字段分布对比六类指标，且数字可用脚本重跑复现。
4. 说明文档可用：README 覆盖依赖、运行命令、目录结构、逐列规则、已知限制。
5. 理解到位：口述时能解释为什么某列选择删除而不是填充、某类异常值选择保留还是剔除。
6. 时间约束达成：按每天 1 小时推进，两周内完成上述 1–4 项。

区分说明：以上是"完成条件"，不是"已完成结果"；当前仅有计划，尚无任何脚本或对照表产出。

## 风险与调整

- 每天仅 1 小时、易被打断：若某天未完成，不再追加时长，直接用第 7 天或第 14 天缓冲吸收；连续落后 2 天以上，启用下面的缩减方案。
- 缩减方案（保交付）：优先保住第 2、3、5、6、10、11、13 天内容（读取、体检、缺失、去重与文本、工程化、对照、README），把第 8、9、12 天的异常值、分组校验、边界测试降为"记录待办"。
- 卡在某个 API 超过 20 分钟：先记录现象并跳过，用最简可行写法（如循环 + 简单判断）替代，把优雅写法留到复盘日。
- 范围膨胀（想顺手学 merge、多层索引、大数据性能、可视化）：严格移到第 14 天的"下一阶段方向"，不插入两周计划。
- 没有真实数据或字段含义不明：先用自造数据跑通全流程，把"真实字段语义确认"列为待确认项；不要为不理解的字段编造清洗规则。
- 过度清洗风险：删除行过多导致数据不可用，或填充掩盖真实缺失。触发条件（如某列删除后剩余行数低于原 50%）时，回退该规则并在对照表中标注原因。
- 数据含敏感信息：若使用真实业务数据，先确认是否允许本地处理与留存清洗后文件，脚本与日志中避免打印完整个人字段。
