# Agent 工具：从普通函数到工具注册与执行

> 主题：工具定义、工具描述、参数结构、Agent 注册与 invoke 调用。
> 示例框架：Deep Agents 与 LangChain。通用概念与具体 API 写法需要区分，其他框架的接口可能不同。

## 示例约定

示例按 deepagents 0.7.8 核对，只保留当前知识点的关键代码。`model` 表示已创建的、支持工具调用的模型客户端，省略连接地址、密钥配置和重复的初始化过程；文中的工具定义均直接给出。

## 工具解决什么问题

模型可以生成文字，也可以提出工具调用请求。读取文件、保存计划等具体操作，需要由程序实际执行。工具把这些操作组织成模型可以请求调用的能力。

例如，模型生成计划正文后，可以请求调用保存文件的工具。真正执行文件写入的是工具函数；工具结果返回后，模型才继续处理。

因此要区分三个环节：

```text
定义工具能力 → 向 Agent 注册工具 → 运行时请求并执行工具
```

定义或注册完成，不代表工具已经执行，也不保证模型每次都会选择它。

## 从普通函数到工具对象

普通 Python 函数可以使用类型注解和返回值，让输入输出更清晰：

```python
def summarize_goal(goal: str) -> str:
    return f"待规划目标：{goal}"
```

类型注解、docstring 和显式的 `return` 并不是普通函数在语法上必需的部分。例如，没有显式 `return` 的函数会返回 `None`。

定义工具时，则应该明确描述用途和输入输出。使用 `@tool` 可以将函数包装为工具对象：

```python
from langchain_core.tools import tool

@tool
def summarize_goal(goal: str) -> str:
    """返回目标的确认信息，不实际执行目标。"""
    return f"待规划目标：{goal}"
```

装饰后，变量 `summarize_goal` 指向的是工具对象。它包含工具名称、描述、参数结构，并提供 `invoke()` 等调用接口。函数体仍然决定实际执行的操作。

### docstring 提供什么信息

docstring 用于说明工具的用途、适用场景和必要限制。参数或返回值有容易误解的地方时，也应解释清楚。

描述应准确、简洁，不是越长越好。例如“返回确认信息，不实际执行目标”，就说明了这个示例工具的能力边界。

模型结合用户请求、系统规则以及工具信息提出调用请求；框架负责执行工具。docstring 本身不会执行函数，也不能强制模型一定按预期选择工具。

### 类型注解提供什么信息

参数名称和类型注解帮助框架生成工具的输入结构，描述调用时需要的字段，并参与输入校验。

例如 `goal: str` 表示工具需要名为 `goal` 的字符串参数。但字符串类型不代表业务内容一定有效：若要求它非空、长度受限或符合特定格式，还需要相应的校验规则。

`-> str` 则说明函数预期返回字符串，不应将 Python 类型注解理解为自动实施所有运行时检查的机制。

## 怎样注册到 Agent

将工具对象放入 `create_deep_agent()` 的 `tools` 列表，向 Agent 提供这项能力。

将上面定义的工具注册给 Agent，再通过用户消息启动调用：

```python
from deepagents import create_deep_agent

agent = create_deep_agent(
    model=model,
    tools=[summarize_goal],
    system_prompt="根据用户需求，使用合适的工具。",
)
result = agent.invoke({"messages": [{
    "role": "user", "content": "请调用 summarize_goal 确认目标：学习文件操作。",
}]})
```

模型名称、服务地址 `base_url`、API Key 等连接配置应在创建模型客户端时设置，不直接作为这里的工具注册参数。

这三个职责可以分开组织：工具定义负责具体操作，模型配置负责连接模型服务，Agent 装配负责注册工具及其他组件。

用户请求工具调用不保证模型必然调用。应在 `result["messages"]` 中同时查找模型的 tool_calls 和对应的工具结果，不能把最终回答中的“已确认”当成工具执行证据。

## 工具的 invoke 与图的 invoke

两者都叫 `invoke()`，但接收对象不同，运行范围也不同。

### 直接执行工具

直接调用上面定义的工具，不需要先构建 Agent：

```python
result = summarize_goal.invoke({"goal": "学习文件操作"})
print(result)  # 待规划目标：学习文件操作
```

根据示例函数体，预期输出为：

```text
待规划目标：学习文件操作
```

这里由代码明确指定工具和参数，没有模型参与选择，也不会调用模型服务。

### 执行 Agent 图

前面注册示例中的 `agent.invoke(...)` 启动的是图运行，过程中可能包含多次模型调用和工具执行：

```text
用户输入
    ↓
模型生成回复
    ├── 普通最终回复 → 运行结束
    └── 工具调用请求 → 框架执行工具
                           ↓
                      结果加入消息
                           ↓
                      再次调用模型
```

模型也可能直接回答，没有调用工具。需要检查实际消息中的工具调用请求和对应工具结果，不能仅凭最终文字断定工具执行过。

`agent.invoke()` 同步等待图运行结束。在此处的 Deep Agents 默认调用方式中，它返回图的最终状态，可以通过 `result["messages"]` 查看消息记录；并不只是返回一句供用户阅读的答案。

| 对比项 | 工具的 invoke | Agent 图的 invoke |
| --- | --- | --- |
| 谁决定执行什么 | 调用代码明确指定工具 | 模型与图的控制流程共同决定运行步骤 |
| 输入 | 该工具要求的参数 | 图的输入，例如 messages；运行配置另行传入 |
| 执行范围 | 指定工具 | 整个 Agent 流程 |
| 返回值 | 工具函数的执行结果 | 示例框架默认方式下的最终图状态 |
| 是否需要请求模型 | 示例直接调用不需要 | 真实模型 Agent 运行时需要 |

## 代码演示：观察工具信息与参数校验

增加一个必填参数，观察输入结构与校验行为；这段只执行工具，不请求模型：

```python
from langchain_core.tools import tool
from pydantic import ValidationError

@tool
def summarize_goal(goal: str, deadline: str) -> str:
    """返回目标和期限，不实际执行目标。"""
    return f"目标：{goal}；期限：{deadline}"

print(summarize_goal.args)  # 查看生成的参数结构
try:
    summarize_goal.invoke({"goal": "学习文件操作"})
except ValidationError:
    print("缺少必填参数 deadline")

result = summarize_goal.invoke({"goal": "学习文件操作", "deadline": "一周内"})
```

相比最初只有 `goal` 的定义，这个工具增加了必填的 `deadline` 参数。可以对照参数结构、缺少字段时的异常和参数完整时的返回值，理解工具输入校验。

这个演示只验证工具定义和直接调用。要验证真实模型是否选择并正确使用工具，还需要创建模型客户端、注册工具，再检查运行中的工具调用请求与对应结果。直接调用成功不能替代这一步验证。

## 容易混淆的地方

- **定义工具不等于执行工具**：函数体提供能力，调用才执行操作。
- **注册不等于调用**：注册意味着可用；是否调用要看实际运行。
- **模型请求调用不等于执行成功**：还需要检查工具结果和实际产物。
- **类型正确不等于业务有效**：业务约束仍需显式实现。
- **工具 invoke 不等于图 invoke**：前者执行指定能力，后者执行完整流程。
- **@tool 装饰后，名字指向工具对象**：直接函数调用与工具接口不同。工具 invoke 会经过输入解析、校验和调用流程，再执行底层函数。
- **同名 invoke 不代表相同执行范围**：工具与 Agent 图遵循 Runnable 调用接口约定；模型并不是生成 Python 的 invoke 代码，而是发出工具名称和参数，由框架处理。
- **普通返回值不等于自动更新任意 state 字段**：工具结果会回到调用流程；需要改变特定图状态时，应使用框架支持的状态更新方式，例如相关工具中的 Command。

## 示例验证范围
