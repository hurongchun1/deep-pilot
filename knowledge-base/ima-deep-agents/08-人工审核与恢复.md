# 08｜Human-in-the-Loop：在动作执行前让人决策

## 适用场景

发布、删除、修改敏感文件等动作可能需要人确认。创建 Agent 时可用 `interrupt_on` 为特定工具及条件配置审核。模型提出调用后，框架在工具执行前暂停，并把工具名称和参数交给调用方。是否审核、允许哪些决定由开发者设计；框架不会自动识别所有业务风险。

| 决定 | 含义 |
| --- | --- |
| `approve` | 按原参数尝试执行；不保证工具一定成功 |
| `edit` | 用审核后修改的参数尝试执行 |
| `reject` | 不执行这次调用，将拒绝反馈给 Agent |
| `respond` | 人直接提供回答，适合询问类工具 |

文件权限规则还能按操作与路径设置 `allow`、`deny` 或 `interrupt`。它与特定工具的 `interrupt_on` 是不同机制，不能假定一条文件规则覆盖所有自定义工具或 Shell 命令。

## 暂停后恢复

审核流程依赖 Checkpointer 保存线程状态。应用展示待审核操作，收到人的决定后，通过 `Command(resume=...)` 和相同 `thread_id` 恢复。若一次审核包含多个调用，要核对决定的数量和顺序。`InMemorySaver` 只在当前进程有效，重启恢复需要持久化检查点。

底层 `interrupt()` 可在非工具节点暂停。恢复时，发生中断的节点会从头重新运行到中断点，因此中断前已有外部副作用的代码可能重复执行；需要幂等设计或把副作用放到合适位置。

## 验收口径

批准代表允许尝试，不等于操作成功。拒绝路径要确认外部状态未变化；批准路径要确认实际副作用。Task 4 的本地发布演示分别验证 approve 增加一条记录、reject 不增加，但它不是完整的浏览器审批 UI。

## 自测问题

一个发布工具被批准后却没有产生发布记录，应检查审核恢复、工具结果还是最终回复？程序重启后无法恢复中断，最可能缺少哪种持久化能力？
