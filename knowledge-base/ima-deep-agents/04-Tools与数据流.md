# 04｜Tools 与数据流：让动作可观察、可核对

## Tool 负责什么

Tool 把一次明确的动作暴露给 Agent，例如搜索、计算、保存、读回、结构检查。好的 Tool 要有清楚的输入参数、返回含义、失败反馈和副作用范围。业务流程不要藏在一个含糊的“万能工具”里，否则难以观察每一步是否成功。

Task 8 把 `list_sources`、`read_source`、`save_plan`、`read_plan`、`check_plan`、`save_preference` 分开。这样可以检验计划是否真正保存、读回和通过结构检查；`check_plan` 的 `ok=true` 只代表章节与非空正文通过，不能证明内容正确。

## 工具结果怎样流到下一步

工具执行后，结果作为 Tool 消息回到对话历史，模型下一轮可以读取并用它构造新的工具参数。Task 1 对比了两种情况：预设模型第二次调用把旧数字 `720` 写死，汇率变化后结果错误；真实模型运行时读取换算结果 `700`，再调用计算工具得到 `756`。这证明那次真实运行串联了工具结果，不表示模型内部长期保存了该值。

对依赖结果的动作要按顺序等待：`save_plan` 成功后调用 `read_plan`，读回成功后调用 `check_plan`。不要在同一批并行调用中假定读取一定发生在写入之后。

## 失败处理与边界

Task 1 的离线实验中，参数类型错误被包装成给模型看的错误反馈；函数内部 `KeyError` 则直接中断 `invoke()`。因此设计工具时要区分可让模型修正的输入错误、真实的程序故障和外部服务失败。不要依据单个实验推断所有工具异常都按同一规则处理。

对于写文件工具，还应限制路径和文件名，避免任意路径写入。Task 8 的 `save_plan` 校验 slug、非空内容和目标是否位于项目目录内。权限与业务校验分别负责不同层面，工具返回“已保存”后仍应读回或检查实际文件。
