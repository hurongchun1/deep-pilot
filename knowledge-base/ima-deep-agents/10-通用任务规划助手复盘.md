# 10｜把五项能力组合起来：通用任务规划助手

## 用户任务

用户描述学习、开发或活动目标；Agent 把目标和约束变成 Markdown 行动计划。计划需要保存、读回并做结构检查。缺少条件时标为待确认，不能把建议写成用户已提供的事实。

## 架构分工

| 能力 | 在 Task 8 中的职责 | 不能替代什么 |
| --- | --- | --- |
| `TodoListMiddleware` | 跟踪理解需求、拆解、保存、检查 | 文件和内容验收 |
| `task-planning` Skill | 提供通用规划方法与提纲 | 具体文件读写 |
| Tools | 发现资料、保存、读回、结构检查、保存明确偏好 | 内容真实性与可行性判断 |
| `MemoryMiddleware` | 在新会话加载规则和长期偏好 | 自动判断所有信息都值得记住 |
| `FilesystemBackend` | 映射虚拟路径到项目文件 | 自动生成或保存计划 |

这个组合的关键不是代码数量，而是职责清楚：Skill 规定步骤，Tool 执行动作，Backend 承载文件，Memory 处理跨会话信息，规划记录过程。

## 一次可靠运行应怎样核对

1. 输入：目标、预期产物、可用时间、限制；缺失项是否正确列为待确认。
2. 资料：是否只读取当前任务相关材料，没有把旧案例规则带入。
3. 过程：是否真实调用 `write_todos`，依赖动作是否按顺序执行。
4. 文件：`save_plan` 成功后是否读回同一文件。
5. 结构：`check_plan` 是否返回 `ok=true`，章节正文是否非空。
6. 内容：计划是否可行、来源是否可靠、时间与用户约束是否一致；这一步仍需人工审阅或额外证据工具。
7. 最终状态：所有应完成的 Todo 是否完成，失败是否明确呈现。

## 已有证据与限制

本项目的离线实验覆盖学习、开发、活动三类输入，验证图、中间件、Skill 读取、偏好加载和文件流程，但模型动作由脚本预设。一次真实模型运行成功生成两周 pandas 学习计划，完成 Skill 读取、Todo、保存、读回和结构检查；另一次真实运行虽然生成文件且结构通过，却留下 `in_progress` Todo，被严格验收拒绝。两者说明：既要看产物，也要看实际轨迹和最终状态。

`check_plan` 只检查必要章节与非空正文。它不会检查计划是否真的能在两周内完成，也不会证明引用的资料可信。后续若要提高质量，应从具体失败案例提炼可执行的内容检查或 Rubric，而不是仅增加一条“请认真检查”的提示词。

## 设计新 Agent 时可复用的提问

“用户要交付什么？什么证据算完成？哪些操作必须由 Tool 执行？哪套方法值得写成 Skill？哪些信息跨会话复用？每类文件放哪里？哪些动作要审核？真实模型有没有按设计执行？”
